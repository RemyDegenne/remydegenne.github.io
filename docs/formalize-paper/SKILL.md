# Formalizing a paper (Lean 4 + Mathlib + LML)

Commands use this repository's names; for another paper substitute the library name
(`Maiti2026Power`), the headline targets (`comparator/targets.txt`) and the paper source (`source/`).

Companion files in this directory:

- `bootstrap.md`: starting from an empty directory (tool installation, project creation,
  blueprint, `formalization.yaml`, comparator, first push), with ready-to-copy files in
  `templates/`.
- `tools.md`: where every tool lives, learning resources, and the gotchas collected on this
  project. Read it when a tool misbehaves or before touching the comparator setup.

## Layout of a project

- `source/`: the paper. `notes/blueprint-outline.md`: the paper decomposed into labelled lemmas
  before any Lean is written; `notes/*.md` also hold design decisions and upstreaming candidates.
- `blueprint/src/chapters/*.tex`: the leanblueprint. Part I follows the paper, Part II holds the
  prerequisites meant for Mathlib/LML (concentration, information theory, algorithms).
- `<Lib>/Mathlib/`, `<Lib>/LeanMachineLearning/`: library-shaped material (no paper-specific
  objects), mirroring the upstream directory layout. `<Lib>/<Paper>/`: the paper itself, one file
  per result.
- `formalization.yaml`: the headline statements and the `status` section (phases, sorry counts,
  what changed and when). `comparator/`: one self-contained challenge per headline theorem,
  generated, never hand-edited.
- Every file is `module` + `public import` + `@[expose] public section`; the root
  `<Lib>.lean` is generated by `lake exe mk_all --lib <Lib>` (CI checks it with `--check`).

## Workflow

1. **Outline first** (`bootstrap.md`, step 3). The outline fixes every label and proof route;
   decide the modelling there (here: LML's `IsAlgEnvSeq` framework on an arbitrary probability
   space, identification algorithms as sampling + stopping + output rules, stopping times as
   Mathlib `hittingAfter`), then write the blueprint chapters from it.
2. **Phase 1, statements.** Define the objects in library generality (generic
   finite-dimensional inner product space rather than `EuclideanSpace`, measures with implicit
   `{mX : MeasurableSpace X}` binders when a measure fixes the σ-algebra, no abbreviations
   that only save typing). State each headline result with `sorry`, list it in
   `formalization.yaml`, generate its comparator challenge. The challenges freeze the
   statements; phase 2 must prove exactly them.
3. **Phase 2, proofs, blueprint-driven.** Before attacking a large target, expand the
   blueprint into a sequence of small labelled lemmas with `\uses`. Then formalize one
   coherent area at a time (a whole prerequisite chapter), not scattered one-step lemmas.
   Prove the general Mathlib-shaped statement and derive the paper's or LML's statement as a
   one-line specialization; state laws as `HasLaw`/`HasCondDistrib`, not `Measure.map`
   equations; give conditional divergences in both composition-product (`_compProd`) and
   integral (bare name) forms.
4. **Keep everything in sync as you go.** Each Lean declaration gets its `\lean{Full.Name}`
   tag and `\leanok` the moment it compiles (proof `\leanok` too). Drop hypotheses the Lean
   proof does not use and say so in the docstring. `theorem` only for headline results and
   big classical theorems; `lemma` for everything else.
5. **Record.** Update `formalization.yaml` (`status`), `notes/upstreaming-candidates.md`,
   the README, and memory notes for non-obvious design facts.

## Looking things up

- API of the pinned Mathlib/LML: grep `.lake/packages/mathlib` and
  `.lake/packages/LeanMachineLearning`; the web only to diff against master before a PR.
- Try statements in a scratch file (scratchpad directory, `lake env lean File.lean`) with
  `#check`, `#synth`, `#print`, `example … := rfl` to test definitional bridges before relying
  on them; `exact?`/`fun_prop` for closing goals.
- Import needed? `LEAN_PATH=$(lake env printenv LEAN_PATH) lean File.lean --setup
  .lake/build/ir/<Module>.setup.json`, no lake lock taken.

## Checking your work

Run after every batch of Lean edits, in this order:

```
lake build <Lib> --wfail               # whole library; warnings fail the build
lake exe runLinter <Lib>               # Mathlib linters; fix everything it reports
grep -rn "sorry" <Lib>                 # must be empty in phase 2
grep -rn "^theorem" <Lib>              # only headline/classical results
lake exe mk_all --lib <Lib>            # after adding or removing a module
```

Blueprint, after any `.tex` change (PDF before web, since web reuses the bibliography):

```
python3 scripts/check-blueprint.py     # env balance, labels, \uses, \input, bib keys
leanblueprint pdf && leanblueprint web # from the repository root
lake exe checkdecls blueprint/lean_decls   # every \lean{} tag names a real declaration
```

`blueprint/lean_decls` is generated by the web build, never edited. To see all LaTeX errors at
once: `cd blueprint/src && xelatex -interaction=nonstopmode -output-directory=../print print.tex`
then `grep -n -A3 "^! " ../print/print.log`.

Comparator, whenever a headline statement or a definition in its closure changes:

```
python3 scripts/make-challenges.py     # challenge-gen --import Mathlib: statements over Mathlib
lake build Comparator                  # no --wfail: "uses sorry" warnings are expected here
scripts/comparator-verify.sh --insecure   # 10–15 min, only when asked; run detached
```

Detached long runs: `setsid nohup … > log 2>&1 &` (background Bash has a ten-minute cap) and
never `pkill -f` a pattern that matches the launching shell. Never commit unless asked; ask
before the full comparator run.
